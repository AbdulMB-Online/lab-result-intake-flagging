# lab-result-intake-flagging

A command line tool, packaged in a Docker container, that reads a lab's result
file, throws out the rows that are broken, flags the results a human should look
at, and keeps the history.

It **never says what a result means for a patient.** It says which boundary was
crossed and by how much. The clinician decides.

> **This document is the team's agreed design, written before any code.**
> Everything below is a decision we settled together. If you want to change
> something here, raise it with everyone first — several of these decisions
> depend on each other.

## The problem

A clinic sends blood samples to an outside lab. The lab sends back result files,
and staff read them line by line looking for values that are out of range. Three
things go wrong:

1. Some rows are broken — a value that isn't a number, a date in a format nobody
   can read, a test code the clinic doesn't recognise.
2. Some results are outside the normal range, or close enough to the edge to be
   worth a second look.
3. Some tests were ordered and no result ever came back.

Nobody keeps a record of which results were flagged, and a nurse can't easily see
how a patient's values have changed over time.

The tool reads the result file and the list of ordered tests, **rejects** the
broken rows with a reason for each, and **flags** the rest against the clinic's
own reference ranges. Every result and every check is saved, so the clinic keeps
a history per patient. You get a report of what needs attention, a list of what
was thrown out and why, and the ability to show one patient's history for a test.

---

## Ground rules

These two are not up for discussion.

**1. Synthetic data only.** Every patient, test, value and reference range in
this project is generated by our own script. No real patient information and no
real lab report goes anywhere in this repository — not in the sample data, not
in a test fixture, not in a screenshot.

**2. The tool flags and reports. It never diagnoses.** It does not interpret what
a result means for a patient and does not recommend treatment. This is why we
don't convert units, why no flag message speculates about a cause, and why the
report states plainly at the bottom that the clinician decides.

## Agreed decisions

### 1. The clean result record

One row of the lab's result file, once we trust it.

| Field | What it holds |
| --- | --- |
| `result_id` | The lab's own ID for this result. We never invent one. It is how we avoid loading the same result twice. |
| `patient_id` | Who the result belongs to. |
| `test_code` | Which test, as a short code (`GLU`, `HGB`, `K`). Forced to capitals on the way in, so `glu` and `GLU` don't become two different tests. |
| `value` | The number. May be empty — see below. |
| `unit` | The unit the lab measured in (`mg/dL`). We store it even though the settings file also has a unit, because comparing the two is the whole point of the wrong-unit check. |
| `collected_date` | When the sample was taken. |
| `reported_date` | When the lab sent the result back. |
| `order_id` | Which ordered test this result answers. **May be empty** — older files don't carry it. |

**Dates are `YYYY-MM-DD` and nothing else.** `03/04/2026` is March 4th in the US
and April 3rd nearly everywhere else. In a clinical tool, guessing between the
two is worse than refusing the row.

**A row is only clean if** every required field is filled in, the test code is
one we know, the value is a real number (or deliberately blank), and the dates
are valid with collection on or before reporting.

**Blank is not the same as broken.** An empty value cell, or a marker like
`PENDING`, `NA` or `N/A`, is *kept* as a clean record with no number in it. That
row still tells you the sample reached the lab, which matters. It gets flagged,
not rejected.

**Broken rows are never silently dropped.** They go on a rejects list with a
reason code, and the report shows them. A validation tool that quietly discards
what it can't read is lying to you.

Reasons we reject a **result** row:

| Reason code | Means |
| --- | --- |
| `MISSING_RESULT_ID` | no ID, so the result can't be referred to or stored |
| `MISSING_PATIENT_ID` | no patient, so the result can't be filed against anyone |
| `MISSING_TEST_CODE` | the test code column was empty |
| `UNKNOWN_TEST_CODE` | the code isn't in the settings file, so there's no range to check against |
| `VALUE_NOT_NUMERIC` | the value isn't a number we can read (`ninety-two`, `9.2.1`, `##ERR##`) |
| `VALUE_NEGATIVE` | the value is below zero |
| `INVALID_DATE` | a date is empty, malformed, or not a real calendar date |
| `REPORTED_BEFORE_COLLECTED` | the lab reported the result before the sample was taken |
| `DUPLICATE_RESULT_ID` | the same `result_id` already appeared in this file |
| `MALFORMED_ROW` | the row has more or fewer fields than the header, so every column is suspect |

Reasons we reject an **ordered test** row:

| Reason code | Means |
| --- | --- |
| `MISSING_ORDER_ID` | no ID for the order |
| `MISSING_PATIENT_ID` | no patient |
| `MISSING_TEST_CODE` / `UNKNOWN_TEST_CODE` | as above |
| `INVALID_DATE` | as above |
| `DUPLICATE_ORDER_ID` | the same `order_id` already appeared in this file |

### 2. The ordered test record

One test the clinic asked for.

| Field | What it holds |
| --- | --- |
| `order_id` | The clinic's ID for this order. |
| `patient_id` | Who it was ordered for. |
| `test_code` | Which test. |
| `ordered_date` | When it was ordered. |

This record exists for exactly one reason: to find tests that were ordered and
never came back.

**How an order is matched to a result:** the result names its `order_id`
directly. One order, one result, no guessing.

When a result has no `order_id` — older files — we fall back to matching on
patient and test code, with the result collected on or after the order date.

> **Why the `order_id` link matters.** Matching on patient and test code *alone*
> would mean **any one** result satisfies **every** order that patient ever had
> for that test. A patient with five glucose orders and one result returned would
> raise zero flags — four unreturned tests, silently missed. That is the exact
> problem the clinic described, so the result record carries `order_id`.

### 3. The patient record

Generated alongside the orders and results, so the history view has something to
show other than an ID.

| Field | What it holds |
| --- | --- |
| `patient_id` | The clinic's ID. Every result and order points at this. |
| `display_name` | A made-up name, for the top of a history page. |
| `birth_date` | `YYYY-MM-DD`. |
| `sex` | `F`, `M` or `X`. |

All of it synthetic, per the ground rules.

### 4. The settings file

`config/settings.json`. The **only** place reference ranges live.

```json
{
  "schema_version": "1.0",
  "borderline_pct": 0.05,
  "tests": {
    "GLU": { "name": "Glucose, Fasting", "low": 70.0, "high": 99.0,  "unit": "mg/dL" },
    "K":   { "name": "Potassium",        "low": 3.5,  "high": 5.1,   "unit": "mmol/L" }
  }
}
```

Each test code gives a **low** limit, a **high** limit, and the **unit** those
limits are written in. `borderline_pct` says how close to a limit counts as
borderline — see the next section.

**If the settings file is missing, unreadable, or wrong, the tool stops with a
message naming the file and the problem.** It never falls back to a built-in
range. A silent default range in a clinical tool is worse than a crash.

The file is checked on load: `low` must be below `high`, limits must be numbers,
the unit can't be blank, and `borderline_pct` must be above 0 and at most 0.5.

The ten test codes we cover: `GLU`, `HGB`, `WBC`, `PLT`, `K`, `NA`, `CREA`,
`TSH`, `CHOL`, `ALT`.

### 5. Out of range, borderline, and missing

#### How close to a limit counts as borderline

The **band** is `borderline_pct` of the width of the range, measured **inward**
from each limit. With `borderline_pct` at 0.05, that's 5% of `high − low`.

One setting, very different bands — which is exactly why it's a percentage and
not a fixed number:

| Test | Range | Unit | Width | Band (5%) | Borderline-low zone | Borderline-high zone |
| --- | --- | --- | --- | --- | --- | --- |
| `K` | 3.5 – 5.1 | mmol/L | 1.6 | **0.08** | 3.50 – 3.58 | 5.02 – 5.10 |
| `TSH` | 0.4 – 4.0 | mIU/L | 3.6 | **0.18** | 0.40 – 0.58 | 3.82 – 4.00 |
| `HGB` | 12.0 – 17.5 | g/dL | 5.5 | **0.275** | 12.000 – 12.275 | 17.225 – 17.500 |
| `NA` | 135 – 145 | mmol/L | 10.0 | **0.50** | 135.0 – 135.5 | 144.5 – 145.0 |
| `GLU` | 70 – 99 | mg/dL | 29.0 | **1.45** | 70.00 – 71.45 | 97.55 – 99.00 |
| `PLT` | 150 – 400 | 10⁹/L | 250.0 | **12.5** | 150.0 – 162.5 | 387.5 – 400.0 |

A band of 0.08 for potassium and 12.5 for platelets, from one number. No single
fixed amount could serve both.

Glucose drawn out:

```
   OUT OF RANGE  │    BORDERLINE    │     no flag      │   BORDERLINE    │  OUT OF RANGE
 ────────────────┼══════════════════┼──────────────────┼═════════════════┼──────────────
               70.0              71.45              97.55             99.0
              (low)           low + band         high − band        (high)
```

#### A value exactly at a limit

**The limits are inclusive, so a value exactly on one is in range — and it is
borderline.**

`HGB 17.5` against a high of 17.5 is a normal haemoglobin. It is not out of
range. But it is the closest a result can get to crossing without crossing, so
it is flagged borderline, and the report says *"exactly at the high limit"*.

Two reasons: reference ranges are conventionally inclusive, and in a clinical
tool "in range but flagged" is the safe direction to err.

#### What we flag

| Flag | When | Severity |
| --- | --- | --- |
| `OUT_OF_RANGE` | the value is below `low` or above `high` | high |
| `BORDERLINE` | the value is in range but inside the band of a limit | medium |
| `MISSING_VALUE` | the result line arrived with no number in it | high |
| `MISSING_RESULT` | a test was ordered and no result came back | high |
| `UNEXPECTED_UNIT` | the unit doesn't match the settings, **or no unit was recorded at all** (added in 1.1.0) | high |

#### One example of each

| Case | Example | Why |
| --- | --- | --- |
| **No flag** | `GLU 85.0 mg/dL` | In 70–99 and well clear of both bands. |
| **Borderline, low side** | `K 3.55 mmol/L` | In range. Band is 0.08, so the zone is 3.50–3.58. Sits 0.05 above the low limit. |
| **Borderline, high side** | `GLU 98.0 mg/dL` | In range. Zone is 97.55–99.00. Sits 1.0 below the high limit. |
| **Exactly at a limit** | `HGB 17.5 g/dL` | Equals the high limit. In range, and borderline at distance 0. |
| **Out of range, high** | `GLU 126.0 mg/dL` | 27.0 above the high limit. |
| **Out of range, low** | `HGB 11.9 g/dL` | 0.1 below the low limit. |
| **Missing value** | `TSH`, value cell blank or `PENDING` | The row is kept — the sample reached the lab — and flagged. |
| **Missing result** | order `ORD-0115`, `PAT-0003`, `PLT`, nothing came back | The flag carries the order ID, because there is no result to point at. |
| **Unexpected unit** | `K 16.4 mg/dL` where the range is in mmol/L | The unit doesn't match, so the comparison can't be trusted. |
| **Rejected, never flagged** | value `abc`, or date `03/15/2026`, or code `XYZ` | Never becomes a result at all. Goes on the rejects list. |

#### The two things people get wrong

**1. The band lives only *inside* the range.** Compare `HGB 17.5` (borderline)
with `HGB 11.9` (out of range). A value just *outside* a limit is not "nearly
borderline" — it is out of range, full stop. There is no overlap and no gap
between the two.

**2. One result can carry more than one flag.** A potassium of `16.4` recorded in
`mg/dL`, against a range of `3.5 – 5.1 mmol/L`, raises **both**
`UNEXPECTED_UNIT` *and* `OUT_OF_RANGE`.

This is deliberate. Each rule reports what it saw, independently. Staff see both
facts — the value crossed a limit, *and* the limit may not apply to it — and
decide for themselves. We do **not** convert the units, because choosing a
conversion factor is interpreting the result, which is the clinician's job.

Because a flag can quote a value whose unit we don't trust, **a flag message
always quotes the value in the unit the lab actually sent**, and the range in the
unit the settings use. The mismatch has to be visible on the line itself.

Keeping the rules independent also means the first release behaves exactly like
the second one minus the unit check, which is what makes the Friday
before-and-after honest.

#### Severity

Every flag carries **high**, **medium** or **low**, and the report sorts by it so
the serious findings are at the top. A nurse reading fourteen flags shouldn't
have to read all fourteen to find the one that matters.

### 6. The database

SQLite. Requires **SQLite 3.37 or newer** for `STRICT` tables — check this
against the Docker base image.

```sql
CREATE TABLE IF NOT EXISTS patients (
    patient_id   TEXT PRIMARY KEY,
    display_name TEXT,
    birth_date   TEXT,
    sex          TEXT
) STRICT;

CREATE TABLE IF NOT EXISTS orders (
    order_id     TEXT PRIMARY KEY,
    patient_id   TEXT NOT NULL REFERENCES patients(patient_id),
    test_code    TEXT NOT NULL,
    ordered_date TEXT NOT NULL
) STRICT;

CREATE TABLE IF NOT EXISTS results (
    result_id      TEXT PRIMARY KEY,
    patient_id     TEXT NOT NULL REFERENCES patients(patient_id),
    test_code      TEXT NOT NULL,
    value          REAL,                -- empty means reported with no value
    unit           TEXT NOT NULL,       -- may be an empty string; the lab sent none
    collected_date TEXT NOT NULL,
    reported_date  TEXT NOT NULL,
    order_id       TEXT REFERENCES orders(order_id),   -- may be empty
    CHECK (collected_date <= reported_date)
) STRICT;

-- One row per rule the tool knows about. Adding a rule is one INSERT,
-- not a change to any table.
CREATE TABLE IF NOT EXISTS rules (
    rule_code   TEXT PRIMARY KEY,
    description TEXT NOT NULL,
    severity    TEXT NOT NULL,
    release     TEXT NOT NULL
) STRICT;

-- One row every time the tool runs.
CREATE TABLE IF NOT EXISTS check_runs (
    check_run_id     INTEGER PRIMARY KEY,
    run_at           TEXT NOT NULL,
    release          TEXT NOT NULL,
    settings_version TEXT NOT NULL,
    results_file     TEXT,
    orders_file      TEXT
) STRICT;

CREATE TABLE IF NOT EXISTS flags (
    flag_id      INTEGER PRIMARY KEY,
    check_run_id INTEGER NOT NULL REFERENCES check_runs(check_run_id),
    rule_code    TEXT NOT NULL REFERENCES rules(rule_code),
    severity     TEXT NOT NULL,
    patient_id   TEXT NOT NULL REFERENCES patients(patient_id),
    test_code    TEXT NOT NULL,
    result_id    TEXT REFERENCES results(result_id),   -- empty for MISSING_RESULT
    order_id     TEXT REFERENCES orders(order_id),     -- empty for most flags
    message      TEXT NOT NULL,
    details      TEXT,                                 -- JSON
    CHECK (result_id IS NOT NULL OR order_id IS NOT NULL)
) STRICT;

CREATE TABLE IF NOT EXISTS rejected_rows (
    rejected_id  INTEGER PRIMARY KEY,
    check_run_id INTEGER NOT NULL REFERENCES check_runs(check_run_id),
    source_line  INTEGER NOT NULL,
    record_id    TEXT,
    reason_code  TEXT NOT NULL,
    reason       TEXT NOT NULL
) STRICT;

CREATE INDEX IF NOT EXISTS idx_results_patient_test ON results(patient_id, test_code);
CREATE INDEX IF NOT EXISTS idx_results_order        ON results(order_id);
CREATE INDEX IF NOT EXISTS idx_orders_patient_test  ON orders(patient_id, test_code);
CREATE INDEX IF NOT EXISTS idx_flags_run            ON flags(check_run_id);
CREATE INDEX IF NOT EXISTS idx_flags_patient_test   ON flags(patient_id, test_code);
```

**Results link to the patient directly**, not through the order. A result can
arrive that nobody ordered, and that's worth spotting — impossible if the only
path to a patient runs through `orders`.

**Every flag belongs to a check run.** Run the tool today, change a reference
range, run it again tomorrow, and you get different flags. `check_runs` records
which run produced which flags, along with the release and settings version that
were in force. Without it you can't answer "why did this flag appear?".

**`severity` is stored on the flag, not looked up from the rule.** If a rule's
importance ever changes, old runs keep the label they actually used. History
should say what happened, not what the rules say today.

**Turn foreign keys on for every connection** — `PRAGMA foreign_keys = ON`. It is
a per-connection setting and off by default, so one `connect()` function should
do it and everything should use that function.

### 8. The two releases

**Release 1.0.0** — the first four rules: out of range, borderline, missing
value, missing result.

**Release 1.1.0 adds one rule, `UNEXPECTED_UNIT`**, and nothing else.

The lab sends a potassium result measured in mg/dL. Our reference range is
written in mmol/L. Those are different scales — like checking a weight in pounds
against a limit set in kilograms — so the comparison means nothing and the staff
need to know.

```
Lab sent:     K = 16.4 mg/dL
Our range:    3.5 - 5.1 mmol/L
→ flagged: recorded in mg/dL, but the reference range 3.5 - 5.1 is in mmol/L;
           any range check on this value is unconfirmed
```

The rule also fires when the lab sends **no unit at all**, for the same reason:
a range we can't confirm the value against.

This rule needs no new data and no change to any table, so going back to 1.0.0 is
just running the old version against the same database. Nothing to undo.

Each release gets a git tag, and the tool can be asked to run as of either
release, so the before-and-after can be shown live.

## Packaging

The tool ships as a Docker image. The container needs:

- the database path supplied as `LAB_DB_PATH`, pointing at a mounted volume so
  the history survives the container
- the settings file mounted in, not baked into the image, so a clinic can change
  a reference range without a rebuild
- input files mounted read-only

## Continuous integration

The workflow in `.github/workflows/ci.yml` runs on pushes to every branch and
on pull requests. It can also be started manually from the Actions tab after
the workflow is merged into the default branch.

The initial CI environment is Ubuntu 24.04 with Python 3.13. This is the current
test environment; the application's Python version and Docker base image still
need to be agreed by the team.

CI installs `requirements-dev.txt`, then `requirements.txt` if present. Add any
application dependencies to `requirements.txt`. If the team adopts a package
layout that requires installing the project, add that installation to the
workflow before running tests. CI checks dependency consistency and requires
SQLite 3.37 or newer before running `python -m pytest -v`.

Name test files `test_*.py` and test functions `test_*`; a `tests/` directory is
recommended. The command discovers the suite automatically, so new tests do not
need individual workflow entries. Tests should use temporary databases and
synthetic data.

To run the same test command locally in an activated virtual environment:

```bash
python -m pip install -r requirements-dev.txt
# When requirements.txt exists:
# python -m pip install -r requirements.txt
python -m pytest -v
```

**No tests is a failing check.** This repository does not have a test suite yet;
the initial workflow will fail until tests are added. Test failures, collection
errors, and dependency installation errors also fail the check.

To enforce passing tests before merging, a repository administrator must add a
branch protection rule or ruleset for `main`, require pull requests, and require
the **Python tests** status check. Run the workflow once so the check is available
to select. Adding this workflow alone does not enforce branch protection. Once
it is merged, teammates should update their branches from `main` to include it.
